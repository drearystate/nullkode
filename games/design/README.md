# Game Design Playbook (Game Studio)

Design knowledge the Game Studio AI follows so built games play like well-made real games. Every rule uses the engine kits' own units and APIs (phaser-2d@1.0.0, three-3d@1.0.0) and is checkable from code, level data or a screenshot.

## Files
| File | What | Budget |
|---|---|---|
| `CORE-RULES.md` | Rules for every game: feel, readability, feedback, pacing, onboarding, UI, mobile, accessibility, performance, audio, session, DON'Ts | ≤ 1,300 tokens |
| `genres/<id>.md` | One card per genre (22): loop, verbs, tuning numbers, level rules, win/lose, mobile scheme, juice, mistakes, matching asset sets | ≤ 700 tokens each |
| `PLAYTEST-CHECKLIST.md` | 39 yes/no items with severity and stage tags, plus automatic checks A1–A7 (jump envelopes, BFS, spawn, speed ratio, touch overlap, contrast) | ~2,300 tokens |
| `INDEX.json` | Genre ids, aliases for matching an idea, token counts, what to include at each stage | data |

Tokens = characters / 4. `INDEX.json` is generated by `python3 build-index.py` (aliases are edited there; counts are measured). Re-run it after any edit.

## How the Studio uses it
1. **Match a genre** once, at the brief: lower-case the idea, then score each genre in `INDEX.json` by its `aliases` (whole-word or phrase hits; longer phrases count more). Take the best score ≥ 1. If nothing matches, the brief's own `genre` string is matched the same way after the brief returns. With no match at all, use CORE-RULES only. Store the genre id with the game, so later calls (steps, changes, playtests) reuse it without matching again.
2. **Brief** (`briefSystem`): add the matched genre card, so loop, verbs, controls and win/lose follow it. CORE-RULES is not needed here.
3. **Plan** (`planSystem`): add the genre card. Its **Assets** line names sets to search first, and its level/progression rules shape the step goals.
4. **Every build step and change step** (`stepSystem`, `changeSystem`): always CORE-RULES plus the genre card, placed after the ENGINE CARD and before STEP_RULES. Both are fixed for the whole build, so keep them in the stable system-prompt prefix (cacheable). Never repeat them in the per-step user message.
5. **Playtester pass** after the step types `level`, `enemies` and `polish` (see `stages.playtest.after`): a separate call with `PLAYTEST-CHECKLIST.md` filtered cumulatively (after `level`: items tagged `level`/`all`; after `enemies`: + `enemies`; after `polish`: every item, the final pass), plus the genre card, the screenshots, the status message and the game files. Run the automatic checks A1–A7 in code first and pass in their results as facts, so the model only judges what code can't. Turn blocker items into a fix step right away. Fold should-fix items into the next step or polish. Polish items are optional.

Step type comes from the step id/goal keywords listed in `INDEX.json → stepTypes` (for example "level", "map", "tiles" → `level`).

## Keeping tokens low
- Include **one** genre card, never several. For hybrids (for example a "platformer roguelite"), take the primary verb's card. The other card's rules are only needed when its systems get built.
- CORE-RULES + genre card ≈ 1,850 tokens per step call, sent once in the cached system prefix.
- Filter the checklist by stage tag: 17 of the 39 items after the level step, 27 after enemies, all 39 only in the final polish pass. Send automatic-check results as one line each.
- Don't paste the cards into chat replies or the person's messages. They are instructions, not content.

## Kit gaps the cards work around (worth fixing in the kits)
- The settings panel has no **reduce motion** toggle. Games read `NK.settings.get("reduceMotion")` (falsy by default). Adding the toggle to `SETTINGS_DEFAULTS` and to `NK.ui.settings` makes those rules work for players.
- `NK3D.character` has no coyote time, jump buffer, variable jump or fall cap. The 3D cards tell the AI to add them in the hero's fixedUpdate. A kit option would make this a one-liner.
- There is no first-person camera mode. `genres/3d-first-person.md` emulates one with a near-zero-distance third-person rig, which needs a playtest.
- There is no vehicle controller (racing 3D drives a kinematic body).
